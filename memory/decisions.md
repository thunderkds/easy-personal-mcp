## 2026-11-07 — Report folders per workspace, and their files: depth 1, name contains "report", relative path only, own routes (HUN-240, HUN-241, HUN-242; FR-089, FR-090, PRD questions 31 and 32)

**Decision**: `kit.report_folders` + `GET /api/kit/reports` list, per non-orphan workspace, the report folders of its repos: a directory directly inside a repo root (no symlink followed) whose lowercase name contains `report` (`reports`, `smoke-reports`), at most 8 per repo, with file count (cap 2000), count of `session-*.json` files, and newest file time. The Kit view shows them as plain text under each workspace row of "Kit by workspace". Reference only: nothing is opened, parsed, stored or acted on. The read is its own route, so `/api/kit/workspaces` keeps its no-file-read guarantee.
**Decision (FR-090, HUN-242, 2026-11-08)**: each folder entry also carries `repo_no`, the 0-based place of the repo in the workspace's repo list, so one repo can be named when two share a folder name. Two more read-only `GET` routes under the same Guard: `/api/kit/report-files` lists the regular files of one report folder to depth 3, newest first, 200 at most, with a relative `path`, `size`, nullable `mtime_utc` and an `openable` flag; `/api/kit/report-file` returns one file's bytes. The server resolves workspace + `repo_no` + `folder` itself, so no request ever carries an absolute path. Every miss is 404 with the fixed body `{"error":"not found"}`, a file over 10 MB is 413. Each path level is opened with `dir_fd` + `O_NOFOLLOW`, which closes the check-then-open window a `realpath` check would leave open. The content type comes from a fixed extension table, never from the content (`svg` deliberately absent), with `nosniff`, `no-store` and `inline`. A `.html` report is served as `text/html`, settled by a 3-Advocate Debate: a route-set `Content-Security-Policy` is useless here because `Guard.send_csp` overwrites it (`src/easy_personal/surfaces/api.py:98-99`) and a route CSP never governs a `blob:` document the page builds, so the script defence is the dashboard CSP the blob tab inherits. **Proven by `/verify HUN-243`, 2026-11-08** (merged `900ee1a`): a repo-authored `evil.html` opened in the tab did not run its script — Chrome's security log names `default-src 'self'` as the blocking directive — and a relative `/api/` fetch inside a blob document cannot even resolve a URL, a second independent barrier. The same CSP also blocked a report's own inline `<style>`, so every report the project generated opened readable but unstyled. **Decision (FR-093, 2026-11-08, owner; merged `a2458f0`)**: allow inline CSS dashboard-wide — the one constant becomes `default-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'`, which the `blob:` tab inherits, so a report keeps its own look. The owner chose this over a separate sandboxed route with a one-time link (stronger isolation, but a `Guard` change plus a route plus a ticket lifecycle) and over stripping the report's CSS to restyle it (loses the author's design, adds a standing sanitiser). A report's `<script>` stays blocked because `script-src` still falls back to `default-src 'self'`, re-proved in a real browser, not assumed. **The invariant that makes this safe, and it is not obvious**: a malicious report can build a CSS exfiltration primitive and the attempt really fires; nothing escapes only because `img-src`, `font-src` and `connect-src` stay absent and fall back to `default-src 'self'`. `/verify` proved it with a real listening sink that recorded no TCP connection. `tests/surfaces/test_api.py::test_csp_keeps_script_and_egress_on_default_src` fails if anyone widens one of those directives, or moves `'unsafe-inline'` anywhere but `style-src`. **Decision (FR-094, 2026-11-08, owner; merged `883dc23`)**: the same constant also gains `img-src 'self' data:`, because FR-093 fixed the CSS but left every embedded screenshot blank — `img-src` was unset, fell back to `default-src 'self'`, and a `data:` URL is not `'self'`. All 7 session reports in the owner's `orderly` project embed their screenshots that way, 11 images. This does not reopen the egress above: a `data:` URL carries its own bytes and makes no network request, and `font-src` and `connect-src` stay absent. `img-src` must stay exactly `'self' data:` — the guard test now pins that value rather than asserting the directive is absent, so `*`, a host, `https:` or `blob:` each fail it. The subtle part, measured in a real `blob:` tab: a `data:image/svg+xml` is the only `data:` image that could in principle fetch, and what stops it is the browser's SVG-as-image rule (no external loads, no script), **not** CSP — so the reasoning must not be carried over to `<object>` or `<iframe>`, where a `data:` document would be live. `data:` is still refused for `<script src>`, `<iframe src>` and `<object data>`.
**Why**: owner, 2026-11-07: "you can depend on the path of projects in the workspace, and mapping the folder reports, report, or something like that to the dashboard, we just show to easy refer, not manage it in anyway". Owner choice (asked): show the relative path `<repo folder>/<report folder>`, not the full path, so NFR-002 and the leak tests stay as they are. The substring match and the separate route are the Supervisor's choice (smaller change, can be undone; PRD question 31 stays open for the owner's review of the match).
**Result**: median read 0.03 s on 160 repos / 10 workspaces; review found one P1 (one open `scandir` handle per sub-folder; fixed, test under a low `RLIMIT_NOFILE`); merged after `/verify` (2026-11-07).
