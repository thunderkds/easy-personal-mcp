## The Problem Space

Every other plug-in has a **repo** as its subject: easy-verifier scores one, easy-context indexes one,
easy-ui-mcp tests one. `personal-mcp` is the only plug-in whose subject is **the person**. It looks across
all projects at how they work with agents (and, later, with the rest of their life), shows it on a dashboard,
warns, proposes improvements, and manages the config that connects their personal tools.

Locked with the user (2026-10-21):

| # | Question | Answer |
|---|---|---|
| Q1 | "Personal" = agent work only, or whole life? | **All** — agent work first; life sources (calendar, finance, health…) later through the same source interface. |
| Q2 | Credentials / tool connections in scope? | **Yes, as managed connectors**: category → provider catalog (Email: Gmail, SendGrid…; Messaging: Slack, Teams, Discord…) → provider-specific config form. Usage-based "suggested to add" list. |
| Q3 | Report audience | **Only the user** in this version (no share/redaction tier yet). |
| Q4 | Connectors generate config, or call provider APIs? | **Config now, proxy maybe later** — v1.1 writes MCP config for existing provider servers + stores secrets in the OS keychain; a direct API proxy for providers with no MCP server is a separate future brainstorm. |
| Q5 | Surface | **Dashboard** with charts, flows, "needs improvement / aware / warning" items — plus MCP tools and CLI. |

Non-negotiables (family conventions, kernel `CLAUDE.md` / verifier `PROJECT_SPEC.md` §Critical Constraints):
- **Local-first**: no network at runtime (v1 / v1.1); HTTP binds `127.0.0.1` only, never `0.0.0.0`.
- **No secrets in output**: secret values live only in the OS keychain; no tool, report, log or dashboard response ever contains one — only `configured: yes/no` and a reference name.
- **Deterministic over AI judgment**: metrics, warnings and the improvement plan come from declared rules over measured facts (the verifier `RatingRule` pattern); no LLM inside the server.
- **Python 3.11+**, one core shared by CLI + MCP (stdio default, streamable-http opt-in), like easy-verifier.
- **Microkernel boundary**: own repo, usable without the kernel; the kernel never depends on it. Pattern and conventions may be copied from siblings; **code is never imported or vendored** (easy-context `PROJECT_SPEC.md` Critical Constraints).
- **Read-only on sources**: never modifies transcripts, traces or other repos.

## Alternative Paths

| Option | Name | Summary | Invasiveness | Code Volume | Regression Risk | Recommended? |
|--------|------|---------|-------------|------------|----------------|--------------|
| A | Analytics only | Usage analytics + rules + static report; connectors dropped | Low | ~1.5k lines | Low | |
| B | One repo, layered, phased | Sources → Core → Surfaces; analytics in v1, connector catalog in v1.1 as an isolated module | Medium | ~3k (v1) + ~2k (v1.1) | Medium | ✅ Yes |
| C | Two plug-ins | `personal-insights-mcp` (analytics) and `personal-connectors-mcp` (secrets/config) as separate repos | High | ~same code, 2× repo overhead | Medium | |

### Option A — Analytics only
**Approach**: parse local agent logs, compute metrics, apply rules, emit JSON + HTML into `reports/`.
**Pros**: smallest, zero secret surface, fully inside existing family conventions.
**Cons**: ignores locked Q2 (managed connectors) and Q5 (interactive dashboard).
**Why it might fail**: delivers numbers but not the "connect my tools" half the user explicitly wants — it would get bolted on later without the boundary designed up front.

### Option B — One repo, layered, phased
**Approach**:
```
sources/      pluggable, read-only adapters → normalized events
  claude_code   ~/.claude/projects/**/*.jsonl  (versioned parser, abstains on unknown shape)
  kit_trace     <repo>/memory/event-trace/*.jsonl  (kernel post_tool_trace.py; spawn usage)
  verifier      <repo>/reports/ easy-verifier JSON  (scores over time)
  git_local     local git log counts per registered repo  (later)
  life/*        calendar, finance, health…  (v2, via the same interface)
core/         store (SQLite in ~/.easy-personal/), metrics, rules, warnings, improvement plan
connectors/   (v1.1) catalog/*.yaml provider schemas, keychain refs, config writer (diff + backup)
surfaces/     MCP tools · CLI · dashboard (static HTML v1, 127.0.0.1:8768 server v1.1)
```
The connectors module is the **only** code allowed to touch the keychain or agent config; core and
sources never import it.
**Pros**: meets every locked decision; one place for a sole maintainer; the module boundary keeps Option C open.
**Cons**: biggest v1 surface of the three; the secret-bearing module shares a process with analytics.
**Why it might fail**:
- Undocumented transcript format changes silently → wrong numbers (**mitigation**: parser pins known shapes, unknown records counted and shown as *abstained*, never guessed; fixture tests per Claude Code version).
- Transcripts contain private text and pasted secrets → leak through a report or tool response (**mitigation**: sources emit counts/metadata only; message text never leaves the parser; a test plants a fake key in a fixture and asserts it never appears in any output).
- Cross-project data in a report lands inside one repo and leaks other project names (**mitigation**: reports default to `~/.easy-personal/reports/`, not a repo `reports/`).
- Scope creep from "all" (Q1) stalls v1 (**mitigation**: v1 ships one source; every new source is its own task).

### Option C — Two plug-ins
**Approach**: split analytics and connectors into separate repos/servers.
**Pros**: strongest isolation — the analytics process never shares memory with secrets; cleanest microkernel story.
**Cons**: two repos, two release trains, two sets of kit artifacts for one maintainer; the "suggested connectors from usage" feature then needs cross-plug-in calls.
**Why it might fail**: maintenance overhead stalls the second repo; the suggestion feature becomes an integration problem.

**Draft v1 tool surface** (frozen once approved, like easy-context's six):
- `usage_summary(period, project?)` — sessions, tokens in/out, cache-hit ratio, est. cost, models
- `usage_breakdown(by=model|project|tool|day, period)` — tables behind the charts
- `session_outliers(period)` — sessions with runaway tool loops (≥ 90 calls, the kernel step-limit), low cache hits, very long contexts
- `warnings(period)` — rule hits labelled `improve` / `aware` / `warning`, each citing rule id + measured value

- `render_report(period)` — writes the HTML dashboard + JSON, returns the path

Configuring a connector is a **dashboard/CLI action, not an MCP tool** — an agent must not be able to write
secrets or rewrite agent config on its own.

**Example v1 rules** (declared, thresholds in config): cache-hit ratio < 50% over 7 days; > 3 sessions/week
hitting 90 tool calls; median session > N tokens without `/compact`; one project > 60% of weekly spend;
cost estimate week-over-week + 50%; days with sessions after a stated quiet hour (life-balance, "aware").

## Edge Case Checklist for TASK_GUIDE

- [ ] Unknown transcript record shape → counted as *abstained* and shown on the dashboard, never coerced into a metric.
- [ ] Planted fake API key / email / message text in a fixture transcript never appears in any tool response, report, log or SQLite row.
- [ ] Missing `~/.claude/projects/` (new machine, other OS path) → clear "no data" state, not a crash or zero-filled charts.
- [ ] Very large transcripts (hundreds of MB) → streamed, incremental ingest keyed by file + offset; re-run is idempotent.
- [ ] Timezone and DST boundaries for "per day" / "per week"; sessions spanning midnight.
- [ ] Cost estimate uses a **dated** local price table; a model missing from it → cost *abstains* for that model rather than guessing.
- [ ] Project names derived from paths → reports stay in `~/.easy-personal/reports/` unless the user sets another dir explicitly.
- [ ] HTTP mode binds `127.0.0.1` only (test asserts `0.0.0.0` is refused).
- [ ] (v1.1) Keychain unavailable (headless Linux, Docker) → connector setup refuses with a clear message; **never** falls back to a plaintext file.
- [ ] (v1.1) Config writer: diff shown, confirmation required, timestamped backup, atomic write; malformed existing `~/.claude.json` → refuse, don't overwrite.
- [ ] (v1.1) No MCP tool can create/modify a connector or read a secret value — asserted by a tool-surface test.
- [ ] (v1.1) Suggestions are counters over metadata (e.g. `gh` invocations, Slack-link domains) — no message text stored.

## Investigation 2026-10-21 — how the pieces actually work

**Trigger:** user: *"let investigate more clearly and give the options again"*.

### Verified facts

| # | Fact | Source |
|---|---|---|
| F1 | Claude Code stores transcripts **in plaintext** under `~/.claude/projects/` and **deletes them after 30 days** by default (`cleanupPeriodDays`). | code.claude.com/docs/en/data-usage — "Local caching" |
| F2 | Transcript lines carry `type`, `timestamp`, `sessionId`, `cwd`, `gitBranch`, `version`, `requestedModel`, and `message.usage` with `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `server_tool_use`, `service_tier`. Record types include undocumented ones (`atis-latch`, `cost-state`, `queue-operation`). | Measured on a live transcript in this session |
| F3 | Claude Code can export metrics/events over **OpenTelemetry** to an endpoint you choose (documented, stable schema; prompt content redacted by default). | code.claude.com/docs/en/monitoring-usage |
| F4 | Claude Code MCP config: `local` and `user` scope live in `~/.claude.json` (a file Claude Code "writes for itself; you don't need to edit it"); `project` scope is `.mcp.json`. Official writer: `claude mcp add` / `claude mcp add-json --scope user`. | code.claude.com/docs/en/mcp, /settings |
| F5 | Claude Code expands `${VAR}` / `${VAR:-default}` in `command`, `args`, `env`, `url`, `headers`; remote servers can use **`headersHelper`** (a command printing JSON headers, run on every connection). | code.claude.com/docs/en/mcp |
| F6 | claude.ai connectors (Gmail, Slack, Notion…) appear in Claude Code automatically **only with a claude.ai subscription login**; not with API keys, Bedrock, etc. Not available to Codex/Cursor. They cannot be created from a local app. | code.claude.com/docs/en/mcp |
| F7 | Codex: `~/.codex/config.toml`, `[mcp_servers.<name>]` with `env`, `env_vars` (forward from environment), `bearer_token_env_var`, `http_headers_helper` (HTTP only). | learn.chatgpt.com/docs/extend/mcp |
| F8 | Cursor: `~/.cursor/mcp.json`, supports `${env:NAME}` interpolation and `envFile`; forum reports interpolation not working in remote `headers`. | Cursor forum threads (not official docs — treat as likely) |
| F9 | Python `keyring`: macOS Keychain, Windows Credential Locker, Linux Secret Service / KWallet. Headless Linux needs an unlocked `gnome-keyring` in a D-Bus session; Docker needs `--privileged`. No backend → `RuntimeError`, plaintext only via opt-in `keyrings.alt`. | keyring.readthedocs.io |

**What this changes:** (1) analytics has a 30-day clock — anything not ingested is gone; (2) there is a documented alternative to parsing transcripts (OTel); (3) the real secret problem is not *storage* but *how the secret reaches the provider server at launch* — every client spawns a command, which gives a clean injection point; (4) `~/.claude.json` should be written through `claude mcp`, not edited.

### D1 — Where analytics data comes from

| Option | How | Pros | Cons |
|---|---|---|---|
| A. Transcripts | Incremental ingest of `~/.claude/projects/**/*.jsonl` | Works today, 30 days of history on day one, rich (per-turn usage, tools, branch, cwd) | Undocumented format (F2), plaintext private content, must ingest before day-30 deletion |
| B. Local OTel receiver | personal-mcp listens on `127.0.0.1` OTLP; user sets `CLAUDE_CODE_ENABLE_TELEMETRY=1` + exporter endpoint | Documented schema, no prompt text by default, also covers Codex if it exports OTel | No history before setup; receiver must be running or data is lost; extra setup |
| C. Both | Transcripts for backfill + detail, OTel as the stable spine | Most robust | Two parsers, de-duplication between them |

**Recommend A for v1, C in v1.2.** A gives value immediately; the ingest runs on a schedule (or a kernel-free `SessionEnd` hook) so the 30-day cleanup never loses data. Unknown record types are counted as abstained.

### D2 — How a secret reaches the provider MCP server (the core connector question)

| Option | How | Secret on disk in plaintext? | Works in |
|---|---|---|---|
| A. Inline in config | `claude mcp add -e SLACK_TOKEN=xoxb-…` | **Yes** (`~/.claude.json`, `config.toml`) | All |
| B. Env reference | Config says `${SLACK_TOKEN}`; you export it in your shell profile | **Yes** (`~/.zshrc`); GUI apps often don't see shell env | Claude, Cursor; Codex via `env_vars` |
| C. Launcher wrapper | Config command = `easy-personal exec slack`; it reads the keychain and execs the real server with env injected. HTTP servers: `headersHelper` / `http_headers_helper` = `easy-personal headers slack` | **No** | All three (Cursor HTTP headers: unverified) |
| D. claude.ai connector | Dashboard links to the official hosted connector (OAuth); nothing local | **No** (held by Anthropic) | Claude only, subscription login only (F6) |

**Recommend C, plus D as a shortcut.** When a provider has an official claude.ai connector and you only need it in Claude, the dashboard says "use the hosted one" and links it. Otherwise C. Cost of C: personal-mcp sits in the launch path of every connector, so `exec` must be tiny, stdlib-only and fail with a clear message if the keychain is locked.

### D3 — How agent config gets written

| Option | How | Risk |
|---|---|---|
| A. Edit files directly | JSON/TOML patch of `~/.claude.json`, `~/.codex/config.toml`, `~/.cursor/mcp.json` | `~/.claude.json` also holds sign-in and project trust; a bad write breaks Claude Code |
| B. Official CLIs where they exist | `claude mcp add-json <name> '<json>' --scope user`; Codex CLI equivalent; file edit only for Cursor (diff + backup) | Depends on CLI flags staying stable; Cursor still a file edit |
| C. Snippet only | Dashboard shows the exact command/JSON; you run or paste it | Zero write risk; more manual |

**Recommend B, with C as the fallback** whenever a CLI is missing or a check fails. The DDR then covers only: keychain writes, `~/.cursor/mcp.json` edits, and running the official CLIs — never project-scope files (kernel-owned).

### D4 — Where secrets are stored

| Option | How | Fits |
|---|---|---|
| A. OS keychain (`keyring`) | Keychain / Credential Locker / Secret Service | Desktop macOS, Windows, desktop Linux. Not Docker, awkward headless (F9) |
| B. Encrypted file | `age`- or `cryptfile`-encrypted store, master passphrase | Headless + Docker; passphrase must be entered or cached somewhere |
| C. External manager | Backend plug for 1Password `op`, Bitwarden, `pass` | If you already use one; adds a dependency |

**Recommend A as default, C as a pluggable backend later, B never as a silent fallback.** No backend available → refuse, explain, offer C.

### D5 — How it runs

| Option | How | Notes |
|---|---|---|
| A. Native (`uv run` / `uv tool install`) | Analytics, dashboard and launcher on the host | Required for D2-C anyway: agent clients spawn the launcher on the host |
| B. Docker only | Like the siblings | Can't reach the keychain (F9); can't be the launcher |
| C. Split | Native launcher + connectors; Docker optional for analytics/dashboard with `~/.claude` mounted read-only | Keeps family Docker parity for the read-only half |

**Recommend A**, with C's Docker image as an optional extra once v1 is stable. This is a deliberate deviation from the siblings and goes in the DDR.

### D6 — Dashboard form (unchanged)

A. static HTML regenerated by CLI (v1, recommended) · B. live `127.0.0.1:8768` server (v1.1, needed for connector forms) · C. both from day one.
